Project Overview 
This project focuses on designing a complete data system — starting from a Transactional 
Database (OLTP) and progressing through to a full Data Warehouse (OLAP). The goal is to 
build a deep understanding of how modern data architectures are structured and how 
information flows through each layer. 
 
Core Learning Objectives 
• Understand the difference between operational (OLTP) and analytical (OLAP) systems 
• Design and implement a normalized transactional database 
• Build an efficient ETL pipeline to move data between systems 
• Architect a scalable Data Warehouse using dimensional modeling 
• Write analytical queries and generate business insights

 Phase 2: OLTP Database Design 
Design a fully normalized transactional database 
 
Objective 
Design a transactional database system that accurately models real-world business operations, 
with proper normalization and integrity constraints. 
 
Requirements 
• Minimum 7–10 tables in the schema 
• Include One-to-Many relationships 
• Include Many-to-Many relationships using junction/bridge tables 
• Apply normalization up to 3NF or BCNF 
 
Constraints to Define 
• Primary Keys on every table 
• Foreign Keys enforcing referential integrity 
• Unique Constraints on business identifiers 
• NOT NULL Constraints on required fields 
• Business rule constraints (e.g., balance cannot be negative, quantity must be > 0) 
 
Deliverables 
• Entity Relationship Diagram (ERD) 
• DDL SQL scripts for all tables 
• Documentation of business rules embedded in the schema 
 
Guiding Questions 
 What are the consequences of incorrectly designed relationships? 
 How would you detect and resolve anomalies in your design?

  Phase 3: OLTP Workload Simulation 
Populate and stress-test the transactional database 
 
Objective 
Simulate real-world database usage by inserting representative data and performing typical 
transactional operations to validate your schema design. 
 
Tasks 
• Insert a meaningful volume of sample data across all tables 
• Perform INSERT operations for new business events 
• Perform UPDATE operations to reflect state changes 
• Perform DELETE operations with cascading or soft-delete logic 
• Execute concurrent transactions to test constraint enforcement 
 
Deliverables 
• SQL seed scripts with sample data 
• Transaction scripts demonstrating CRUD operations 
 
Guiding Questions 
 Can your system handle continuous, concurrent operations efficiently? 
 Do your constraints correctly prevent invalid data from being inserted?

 Phase 5: ETL Design 
Build the data pipeline from OLTP to Data Warehouse 
 
Objective 
Design and document the Extract, Transform, Load process that moves data from the 
operational OLTP system into the analytical Data Warehouse. 
 
Tasks 
• Define source-to-target column mappings for every table 
• Identify and handle missing values with appropriate strategies 
• Detect and eliminate duplicate records 
• Resolve data type inconsistencies between source and target 
• Design transformation logic (e.g., currency conversion, date standardization) 
 
Optional Tools 
• SQL — stored procedures or views for transformation 
• Python — pandas/SQLAlchemy for scripted ETL 
• Apache NiFi or similar ETL orchestration tool 
 
Deliverables 
• ETL flow diagram showing Extract → Transform → Load stages 
• Source-to-target mapping document with transformation rules 
 
Guiding Questions 
 Is your source data clean enough to load directly, or does it require significant 
transformation? 
 How will you handle late-arriving or out-of-order data?

  Phase 7: Advanced Modeling Concepts 
Apply enterprise-grade data warehouse patterns 
 
Objective 
Extend your Data Warehouse design with advanced concepts that handle real-world 
complexities like historical tracking, degenerate attributes, and sparse event data.

Required Concepts 
Surrogate Keys 
Replace natural business keys with system-generated integer keys for all dimension tables to 
ensure stability and join performance. 
 
Slowly Changing Dimensions (SCD) 
• Type 1 — Overwrite: Update the existing record. No history preserved. 
• Type 2 — Add New Row: Insert a new record with effective dates. Full history 
maintained. 
 
Optional Advanced Concepts 
• Junk Dimension — Combine low-cardinality flags into a single dimension table 
• Degenerate Dimension — Store transaction IDs directly in the fact table (no separate 
dim table) 
• Factless Fact Table — Record events that have no measurable values (e.g., enrollment, 
attendance) 
 
Deliverables 
• Written explanation of each concept applied, linked to your specific design 
• SCD Type 2 example showing before/after rows with effective dates 
 
Guiding Questions 
 How will you track changes in customer address, category, or name over time? 
 Which dimensions in your design are candidates for SCD Type 2?

  Phase 8: Performance & Scalability 
Design for large-scale data volumes 
 
Objective 
Ensure your Data Warehouse can handle millions of records efficiently through a deliberate 
indexing and partitioning strategy. 
 
Tasks 
Indexing Strategy 
• Define bitmap indexes on low-cardinality dimension columns 
• Define B-tree indexes on foreign keys and frequently filtered columns 
• Document which columns are covered by each index and why 
 
Partitioning Strategy 
• Apply range partitioning on fact table date columns 
• Consider hash partitioning for even data distribution 
• Explain partition pruning and how it reduces query scan range 
 
Deliverables 
• Indexing plan document with justification for each index 
• Partitioning design with expected query performance improvement 
 
Guiding Questions 
 Can your system handle hundreds of millions of fact table rows without degradation? 
 How does partition pruning reduce I/O in date-range analytical queries?
